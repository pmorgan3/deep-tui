# Plan: durable, resumable, forkable conversations

## Outcome

The TUI becomes a real conversation rather than a visual list of independent
runs. Users can start, list, resume, rename, and fork conversations; model
history survives process restarts; headless commands can intentionally join a
session; and storage remains replaceable by plugins.

## Current constraint

Every `DefaultAgentService.run()` currently constructs a new message array
containing only the system prompt and newest user input. `TuiState.events`
persists for the lifetime of the screen, which looks conversational, but it is
presentation state and is never sent back to the model. It must not become the
durable format.

## Canonical model

Add stable identifiers and storage-neutral records to the SDK:

```ts
interface Conversation {
  id: string
  title: string
  projectRoot: string
  createdAt: string
  updatedAt: string
  provider: string
  model: string
  parentId?: string
}

type ConversationRecord =
  | { seq: number; type: 'user'; messageId: string; text: string; createdAt: string }
  | { seq: number; type: 'assistant'; messageId: string; text: string;
      reasoning?: string; toolCalls?: ToolCall[]; usage?: ModelUsage;
      createdAt: string }
  | { seq: number; type: 'tool'; messageId: string; toolCallId: string;
      name: string; content: string; createdAt: string }
  | { seq: number; type: 'run'; runId: string; usage?: ModelUsage;
      status: 'complete' | 'cancelled' | 'failed'; createdAt: string }
```

Records preserve exactly what must be replayed to the provider, including
assistant tool calls, their tool responses, and provider-required reasoning
content. API keys, authorization headers, inherited environment variables,
terminal frames, overlays, viewport positions, and theme state are excluded.

Use UUIDs generated by the runtime and monotonically increasing sequence
numbers allocated by the store. Timestamps are ISO-8601 UTC. Record and index
schemas start at version 1 and reject unknown future major versions with a
clear migration error.

## Service and store contracts

Mount a `ConversationService` from the runtime and let plugins register stores:

```ts
interface ConversationStore {
  id: string
  priority?: number
  create(input: CreateConversation): Promise<Conversation>
  get(id: string): Promise<Conversation | undefined>
  list(query?: ConversationQuery): Promise<readonly Conversation[]>
  read(id: string): AsyncIterable<ConversationRecord>
  append(id: string, expectedSeq: number, records: readonly NewConversationRecord[]): Promise<number>
  update(id: string, patch: ConversationPatch): Promise<Conversation>
  remove(id: string): Promise<void>
  fork(id: string, throughSeq?: number): Promise<Conversation>
}
```

`ConversationService` selects the highest-priority store, validates IDs and
record order, exposes subscriptions, and provides message-history conversion.
Optimistic `expectedSeq` prevents two processes from silently interleaving one
conversation. A conflict tells the caller to reload; automatic merging is out
of scope.

If no durable store is registered, the service provides an explicitly
ephemeral in-memory conversation for backward-compatible use. The TUI labels
it ephemeral rather than pretending it can resume.

## Filesystem store plugin

Create `@deep-tui/plugin-session-files` using the project-path service:

```text
.deep-tui/sessions/
  index.json
  <conversation-id>.jsonl
```

- `index.json` contains schema version and lightweight conversation metadata.
- Each JSONL starts with metadata and appends canonical records.
- Open files with restrictive permissions where supported.
- Serialize appends per conversation inside a process and use a lock file with
  stale-lock diagnostics for cross-process writers.
- Flush complete newline-delimited records. On load, tolerate only an
  incomplete final line caused by a crash; malformed earlier records fail.
- Rebuild a missing/corrupt index from valid logs through `deep-tui sessions
  repair`; do not silently discard logs.
- Compact only through an explicit maintenance operation.
- Fork initially copies records through the chosen sequence and records
  `parentId`; this costs storage but avoids parent-deletion and mutable-lineage
  hazards.

Configuration includes `directory`, `maxSessions`, `maxRecordBytes`, retention
days, and `persistToolOutputs`. The latter defaults true because tool responses
are required for exact provider replay; disabling it clearly marks resumed
history as lossy.

## Agent integration

Extend `AgentRunOptions` with `conversationId` and `runId`. The default agent:

1. Loads existing records and converts them to `ModelMessage[]`.
2. Renders the current system prompt separately so policy updates can take
   effect without storing duplicate system messages.
3. Appends the user record before starting the provider request.
4. Appends each completed assistant/tool record in canonical order, including
   provider usage on each assistant response when available.
5. Appends a terminal run record with usage/status.
6. Leaves a cancelled or failed run auditable and resumable without inserting
   a fake assistant answer.

Streaming deltas are presentation events; only completed canonical messages
are appended. If the user cancels after partial assistant text, offer a
configurable choice: discard it by default, or store a record explicitly
marked partial. Never replay a partial tool-call JSON object.

The service enforces provider model-history invariants. DeepSeek reasoning
content needed around tool calls is retained for replay but remains hidden from
ordinary renderers unless a plugin opts in.

## TUI and command interaction

Add `conversationId`, title, and persistence status to `TuiState`. Starting the
TUI without a requested session creates one lazily on the first submitted
prompt. Subsequent prompts use that ID.

Plugin-provided commands:

- `/new [title]`: finish/cancel current work, then create a blank conversation.
- `/sessions`: interactive recent-session picker with date/model/title.
- `/resume <id>`: load canonical records, rebuild presentation events, and
  reset the viewport to the tail.
- `/fork [seq]`: clone through the selected/current point and switch to it.
- `/rename <title>`.
- `/session`: current metadata and token/cost totals.

The picker previews metadata, not message contents by default. Resume while an
agent run is active is rejected. TUI reconstruction uses a dedicated adapter
from canonical records to event-view models; it does not persist ANSI lines.

Headless CLI options:

```text
deep-tui run --session <id> "continue this"
deep-tui run --new-session "start this"
deep-tui sessions list|show|export|delete|repair
```

Deletion requires confirmation in a TTY or `--yes` in scripts. Export supports
canonical JSON and readable Markdown with explicit warnings around stored tool
output.

## Verification

Test canonical conversion with multi-step parallel tool calls, empty assistant
text, reasoning content, usage, failure, and cancellation. Store tests cover
append ordering, expected-sequence conflict, process restart, truncated final
line, corrupt middle line, atomic index writes, stale locks, retention, fork,
delete, and index repair.

An end-to-end test runs prompt A, closes the composition, starts a new
composition, runs prompt B in the same conversation, and asserts the provider
received A, its tool records, and B in the correct order. A fork test proves
new records never appear in the parent.

## Acceptance criteria

- Follow-up prompts include previous canonical conversation history.
- Conversations survive a fresh process and can be listed/resumed/forked.
- Crash recovery never silently invents, reorders, or drops valid records.
- Session files contain no credentials or presentation-only terminal data.
- A third-party database/cloud store can replace filesystem storage through
  the public contract.
- Running without a durable store remains possible and is visibly ephemeral.
